# 第一性原理分析：上下文压缩是 newbee 全部 thesis 的裂缝

> 2026-08 · 深度改进提案（已实现）。对应代码：`lib/newbee/archive.ex`、`lib/newbee/agent/loop.ex`、`lib/newbee/reader.ex`、`lib/newbee/session.ex`。

## 0. 结论先行

newbee 的全部 thesis 是一句话：**LLM 看到的上下文不是日志，而是日志的物化视图**（DESIGN §4.6）。
由此推出四条可检验的承诺：

| # | 设计承诺 | 实现现实（改动前） |
|---|---|---|
| 1 | 压缩改视图不动日志，原始事件永远完整 | ❌ `Session.rewrite/2` 用摘要**覆写** `messages.jsonl`——日志被压缩本身销毁 |
| 2 | pull over push：知识按需拉取 | ❌ `Newbee.read` 有 `memory://`/`bindings://`/`events://`…唯独没有 `history://`——模型**无法拉取自己最富信息量的资产：它的对话本身** |
| 3 | 确定性压缩优于 LLM 摘要（§6.2） | ❌ 压缩是纯 LLM 散文摘要，失败即"（摘要失败，历史已截断）" |
| 4 | 反事实回放：任意时点可重建 | ❌ 覆写后不可重建 |

这不是一个 bug，是**架构裂缝**：系统的中间内存层（压缩记忆）既不无损、不可寻址、也不确定。
对照经典内存层级：寄存器（bindings ✅ 已实现且优秀）、高速缓存（近期消息 ✅）、主存（压缩摘要 ❌ 一次电话游戏）、磁盘（事件日志 ⚠️ 环境事件有 EventStore，会话日志却会被覆写）。

## 1. 三处级联的信息衰变（为什么"再加点摘要"修不好）

1. **截断在摘要之前**：`summarize_conversation` 先把每条消息 `String.slice(0, 240)` 再喂给摘要器。工具结果（文件内容、报错、测试输出——agent 工作的事实载荷）在第一次压缩就丢了大部分。
2. **摘要的摘要（电话游戏）**：第二次压缩把上一次的摘要当普通消息再次压缩——信息按几何级数衰减，无层级、无合并纪律。
3. **散文不可寻址**：一段 ≤500 字的中文散文没有结构、没有锚点，模型无法引用其中任何一条事实，也无法回溯原文。

## 2. 方案：把中间层做成真的——分层、可寻址、无损的会话档案库

### 2.1 LSM-tree 式压缩（一次蒸馏，永不重蒸）

```
transcript（append-only，永不覆写）
   │  compact: 归档区间 [prev_cut, new_cut) → seg-000N.jsonl（内容寻址，sha256）
   ▼
ledger（compactions.jsonl，append-only，自校验 tail_sha 锚）
   │  每段一次 LLM 蒸馏（从全保真抽取物，非 240 字截断）→ digest 事件（可补写，不改历史）
   ▼
视图 = [system 基底] ++ [汇总消息（确定性装配，零 LLM）] ++ [近期消息原文]
```

- **段（segment）不可变**：digest 每段只算一次、从原始消息算，永不"摘要的摘要"；
- **装配是确定性的**：视图构建零 LLM 调用——新段全量、旧段首行+指针，按 token 预算滑窗；
- **digest 是事件**：蒸馏失败可后续补写（`digest` 事件追加），历史 compaction 事件永不改；
- **崩溃安全**：段文件 tmp+rename 原子写；账本尾行损坏 → 整条忽略（截断恢复，同 EventStore 纪律）；`tail_sha` 锚校验账本与 transcript 是否对齐，不对齐则优雅降级为原始视图。

### 2.2 确定性事实账本（§6.2 原则回归压缩）

压缩时先用**解析**（零 token、零失败）从归档区间提取类型化事实，LLM 只补叙事：

- `user_intents`：用户消息**逐字**保留（意图脊柱，永不衰减，永不摘要）；
- `files`：工具代码中解析出的文件路径（写了/改了什么）；
- `errors`：`✗ error` 签名 + 后续是否 `✓` 解决（对话级"失败抗体"）；
- `results`：`✓ ok` 首行（验证过的事实）。

LLM 摘要失败 → 确定性账本仍然完整（不再有"历史已截断"这种灾难回退）。

### 2.3 `history://`——补上 pull over push 缺的最后一块

```
Newbee.read("history://")              档案索引：段清单、span、token、意图首行
Newbee.read("history://s/seg-0003")    段 digest + 事实账本
Newbee.read("history://s/seg-0003/raw") 段原始消息（全保真）
Newbee.read("history://q/关键词")       跨段全文检索（找回"两小时前那个报错"）
Newbee.read("history://files")         本会话碰过的所有文件
```

工具面不变（光头原则不破）：不加任何工具，只扩唯一读取接口的 scheme。
peer 求值节点经 `Newbee.Host.call` 回主节点执行（跨节点正确）。

### 2.4 与既有机制的相容性

- **provider 前缀缓存**：摘要消息固定在位置 2（system 之后），两次压缩之间消息列表仍然只追加——缓存语义与旧实现一致（任何压缩都会打断前缀缓存，这是 RUM 猜想的固有代价，本方案没有变更它）；
- **repair_history**：视图构建后照常修补悬空 tool_calls；
- **J-Space 恢复提醒**：压缩后注入逻辑保留；
- **旧会话**：无账本的会话视图 = 原始消息（逐字节兼容旧行为）；
- **TUI/CLI 回放**：仍读全量 transcript（UI 永远看得到完整历史）。

## 3. 效果

| 维度 | 改动前 | 改动后 |
|---|---|---|
| 压缩后信息 | 一次性散文 ≤500 字 | 意图脊柱逐字 + 类型化事实 + 分段 digest + 全文可拉取 |
| 第二次压缩 | 摘要的摘要（几何衰减） | 确定性装配（零衰减、零 LLM） |
| LLM 失败 | "历史已截断"（灾难） | 确定性账本兜底（无损） |
| 会话日志 | 被覆写（不可审计/回放） | append-only + 自校验账本 |
| 模型找回细节 | 不可能 | `history://q/...` 一次读取 |

## 4. 为什么这是"最重要的一个点"

上下文极简主义是三条第一性原则之首，压缩是它在长会话里唯一的守门人。
守门人本身在销毁日志，等于 thesis 在自己的核心机制处失效。
修好它，"知识住环境不住 prompt"才第一次对**会话知识**成立——而这正是 agent 最贵、最不可再生的知识。
